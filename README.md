# OneByOne

ルールを差し替えて利用できる、ソースコード改修用のデスクトップアプリです。Windows / macOSの専用ウィンドウから対象を選び、**1ファイルごとに独立したAIコンテキストで修正し、機械検証と別コンテキストの独立レビューを行います**。同じ処理を呼び出すCLIも用意しています。

本体はGo、画面はWails v2 + React / TypeScript、AI接続はOpenAI、Azure OpenAI / Microsoft Foundry、Claude（Anthropic）に対応します。ソースの変更は専用Git worktreeに保存し、元のチェックアウトへの反映は利用者が差分を確認して行います。

AI処理の内部構成、利用ツール、実際のプロンプト、Mermaidの処理フローは[AI処理のハーネス](docs/ai-harness.md)にまとめています。

画面の補足説明は、項目名の右にある「？」にマウスを重ねるか、キーボードでフォーカスすると吹き出しで表示します。クリックで開いたままにでき、再クリック・外側のクリック・Escで閉じます。

ワークスペース名の右にエラーアイコンがある場合、吹き出しのエラーをクリックすると該当タブ・明細へ移動します。ルールの読み込みエラーも明細で確認できます。ワークスペースやルールの削除は、それぞれのヘッダーのゴミ箱から行います。確認後に削除し、処理対象のソースは保持します。

## Windowsで配布用Setupを作る（最短手順）

Windows 10/11（x64）で、ソースをダウンロード・展開済みの場合の例です。`winget`とインターネット接続を使います。

**1. 初回だけ、PowerShellでビルド用ツールを導入します。**

```powershell
winget install -e --id GoLang.Go --source winget --accept-package-agreements --accept-source-agreements
winget install -e --id OpenJS.NodeJS.22 --source winget --accept-package-agreements --accept-source-agreements
winget install -e --id NSIS.NSIS --source winget --accept-package-agreements --accept-source-agreements
```

**2. ターミナルを完全に閉じて開き直し、OneByOneのフォルダで実行します。**

`cd`のパスは、ダウンロードしたソースの場所に変更してください。

```powershell
cd "C:\ダウンロードした場所\OneByOne"

go install github.com/wailsapp/wails/v2/cmd/wails@v2.15.0
$env:WAILS_BINARY = "$(go env GOPATH)\bin\wails.exe"
$env:MAKENSIS_BINARY = "${env:ProgramFiles(x86)}\NSIS\makensis.exe"

npm.cmd --prefix frontend ci
npm.cmd run package -- --platform windows/amd64
```

**3. 生成されたSetupを配布します。**

```text
build\package\OneByOne-windows-amd64-Setup.exe
```

`package`はビルドと梱包をまとめて行い、Git・ripgrep・WebView2導入用ファイルも自動取得して同梱します。最短手順なのでテストは含めていません。テストする場合はパッケージ作成前に`npm.cmd test`を実行します。詳細は[ビルド・配布手順](docs/build.md)を参照してください。

**修正版を配布するとき**は、更新したソースからもう一度パッケージを作ります。既存の出力は上書きしないため、たとえば日時付きの出力先を指定します。

```powershell
$packageOut = "build/package/OneByOne-windows-amd64-$(Get-Date -Format 'yyyyMMdd-HHmmss')"
npm.cmd run package -- --platform windows/amd64 --out $packageOut
```

配布するSetupは、指定した出力先に `-Setup.exe` を付けたファイルです。利用者はOneByOneとCLIを終了し、新しいSetupを実行するだけで更新できます。事前のアンインストールは不要で、ワークスペース・LLM接続設定・認証情報は保持します。

**アンインストール**はWindowsの「設定 → アプリ」のOneByOne、またはスタートメニューの「OneByOne → Uninstall OneByOne」から行います。直接実行する場合は `%LOCALAPPDATA%\Programs\OneByOne\Uninstall.exe` です。アンインストールでも利用者の設定・実行結果は残ります。

## 1. 事前準備

### 対象ソースと実行環境

- 修正対象は、**初回コミット済みでリポジトリ全体に未コミットの変更がないGitリポジトリ**に用意します。リポジトリ内のサブフォルダも指定できます。
- Gitとripgrep（`rg`）は配布物に同梱します。利用者による別途インストールは不要です。CLIでも同梱版を使用します。
- デスクトップ版は起動時に同梱Gitを確認し、不完全な配布や起動失敗があれば専用画面で再展開・再インストールを案内します。
- 対象ソースはUTF-8 / Shift_JISを自動判別し、元の文字コード・BOM・改行形式を保持して編集します。無効な文字列やバイナリ、Shift_JISで保存できない追加文字は理由を記録し、文字化けさせて保存しません。ファイル容量による固定の処理上限はありません。
- 対象プロジェクトのビルド・テストはアプリ外で実施します。必要なツールと依存関係は、そのプロジェクト側で用意してください。

WindowsのSetupにはWebView2のオフライン導入用ファイルを含め、未導入・必要バージョン未満の場合に導入します。開発・ビルドに必要なOS依存環境は[Wailsのインストール手順](https://wails.io/docs/gettingstarted/installation/)を参照してください。

### rules.jsonを用意する

ルールはUTF-8のJSONファイルに、Markdown文字列の配列として保存します。ZIP形式の`.oborules`は使用しません。

```json
{
  "rules": [
    "---\nid: 1\nname: 保存成功後の通知\ndescription: 保存が成功した場合だけ後続処理へ通知し、既存のエラー処理を維持する。\npath_pattern: 'src/**/*.ts'\ncontent_pattern: '\\.save\\s*\\('\n---\n\n# 変更概要\n\n保存完了を確認してから通知する。失敗やリトライ途中には通知しない。\n\n# 変換前\n\n```ts\nawait store.save(record);\n```\n\n# 変換後\n\n```ts\nawait store.save(record);\nawait events.saved(record.id);\n```\n\n# 補足\n\n周囲の例外処理と、通知が一度だけ行われる契約を維持する。\n\n# 変換を保留にすべきケース\n\n通知先や通知対象のIDを判断できない場合。\n\n# 修正後に残っていてはいけないパターン\n\n保存が失敗した場合にも通知する処理。\n"
  ]
}
```

配列内の各文字列は、次のようなYAML front matter付きMarkdownです。JSON内では改行が`\n`、バックスラッシュが`\\`として保存されます。画面では通常の改行として編集できます。

````markdown
---
id: 1
name: 保存成功後の通知
description: 保存が成功した場合だけ後続処理へ通知し、既存のエラー処理を維持する。
path_pattern: 'src/**/*.ts'
content_pattern: '\.save\s*\('
---

# 変更概要

保存完了を確認してから通知する。失敗やリトライ途中には通知しない。

# 変換前

```ts
await store.save(record);
```

# 変換後

```ts
await store.save(record);
await events.saved(record.id);
```

# 補足

周囲の例外処理と、通知が一度だけ行われる契約を維持する。

# 変換を保留にすべきケース

通知先や通知対象のIDを判断できない場合。

# 修正後に残っていてはいけないパターン

保存が失敗した場合にも通知する処理。
````

`id`・`name`・`description`は必須です。空白だけの値は無効で、画面では次へ進めず、ルールを選び直した時や次へ進もうとした時に一覧と詳細へエラーを表示します。`id`は英数字で始まる64文字以内の英数字・ハイフン・アンダースコアで、ファイル内で重複できません（大文字・小文字は区別しません）。実行結果や履歴はIDでルールと結び付くため、作成後は変更できません。数字の連番（`1`、`2`…）を推奨し、画面で追加するルールには次の番号を初期入力します。本文の見出しや構成は自由です。`description`はAIがルールを選ぶための説明、本文は詳細な判断・修正・レビューの指示として使います。

| 条件 | 意味 |
|---|---|
| `path_pattern` | 対象フォルダを起点にした相対パスのglob。例: `src/**/*.tsx`。空欄ならパスで絞り込まない |
| `content_pattern` | ファイル本文に一致する正規表現。空欄なら内容で絞り込まない |
| 両方指定 | パスと内容の両方に一致するファイルが、そのルールの候補 |
| 両方空欄 | 全ファイル共通のルール |

いずれかのルールに一致するファイルが候補になります。Git内部ファイル、依存関係や生成物、設定・認証関連ファイルなど、アプリの固定除外は常に適用します。正規表現は同梱ripgrepで照合します。

ルールには実行コマンドや旧シンボル定義ファイルを含めません。修正後に残してはいけないコードや契約はMarkdown本文に記載し、独立レビューの判断材料にします。本文の見出しから機械的な残存検査を生成する機能はありません。対象プロジェクトのビルド・テストはアプリ外で実施してください。

名称は1〜200文字、各ルールは4 MiB以内、全体は32 MiB以内・5,000件までです。これは取込時の定義検証で、処理中の計画件数や対象ファイル容量の制限とは別です。LLM接続・対象フォルダ・料金単価・実行結果はワークスペース側で管理し、ルールのインポートでは変更しません。

### JSON・CSVを取り込む

ルール一覧の「＋」の右にある「…」からJSON・CSVのインポートとJSONの書き出しを行います。既存ルールがある場合は「マージ」または「上書き」を選びます。マージは現在のルールを残して追記し、上書きはルール一覧を置き換えます。ルールIDはファイルの`id`を使います。マージで同じIDが既にある場合は、読み込んだ側に`_2`、`_3`…を付けて追加します。実行済みの履歴は保持します。検証に失敗した場合は現在のルールを変更しません。元の入力ファイルも変更しません。

CSVは`id,name,description,path_pattern,content_pattern`の5列が必要です。列の値はid・name・descriptionが必須です。それ以降の列は、ヘッダーをMarkdownのH1、セルをその本文として、列順に組み立てます。

```csv
id,name,description,path_pattern,content_pattern,変更概要,補足
1,保存後の通知,成功後だけ通知する,src/**/*.ts,\.save\s*\(,保存成功を確認してから通知する。,失敗時は通知しない。
```

カンマ・改行・ダブルクォートを含むセルはCSVの引用符で囲みます。保存済みルールの書き出し先は`rules.json`です。ロックファイルや実行結果は書き出しません。

### LLM接続情報を用意する

左メニューの「LLM接続」にある「＋」から接続を追加します。名前を付け、OpenAI・Azure・Claudeからプロバイダーを選ぶと、対応する設定欄に切り替わります。ワークスペースを作る前にも登録でき、同じ接続を複数のワークスペースで利用できます。

| プロバイダー | 設定内容 | キー・手動トークンの環境変数 |
|---|---|---|
| OpenAI | APIのベースURL、モデル名、APIキー | `OPENAI_API_KEY` |
| Azure OpenAI / Microsoft Foundry | リソースURL、デプロイ名、認証方式。OAuthではテナントID・クライアントIDとMicrosoftサインイン | `AZURE_OPENAI_API_KEY` / `AZURE_OPENAI_AUTH_TOKEN`（OAuthでは使用しない） |
| Claude | Anthropic APIのベースURL、モデル名、APIキー | `ANTHROPIC_API_KEY` |

OpenAIの既定URLは`https://api.openai.com/v1/`、Claudeは`https://api.anthropic.com/`です。AzureはリソースURL、`/openai/v1/`で終わるURL、または`/responses`の完全URLを受け付けます。モデル名を固定の一覧から推測せず、利用可能なモデル名（Azureではデプロイ名）を入力します。ツール呼び出しと構造化出力に対応したモデルが必要です。

Azureでは「Microsoft Entra ID（OAuth）」を選び、「Microsoftでサインイン」から本人のブラウザーで認証できます。組織のEntraアプリ登録とリソースへの利用権限が必要です。登録手順・対応する接続先は[Azure OAuthの設定](docs/azure-oauth.md)を参照してください。OpenAI・ClaudeはAPIキー認証を使います。

GUIのLLM接続は、名前付きの接続一覧として各ユーザーの端末に保存します。接続先・モデル・認証方式・APIキー・OAuthのトークンキャッシュを含めてAES-256-GCMで暗号化し、ワークスペースJSONには保存しません。API呼び出し時にはGo側のメモリで復号して使用します。初回に暗号用のランダムな32バイト鍵を生成します。Windowsではこの鍵も現在のユーザーのDPAPIで保護し、macOSでは所有者だけがアクセスできるフォルダ・ファイル（`0700` / `0600`）に保存します。macOS Keychainは使用しません。

macOSでは鍵と暗号化設定の両方を取得できる人は復号できます。同じユーザーとして動く別プロセスや管理者から秘密を隔離するものではありません。鍵を失うと保存済み接続は復元できません。

保存済みLLM接続の形式が非対応、またはデータの破損・復号失敗で読めない場合は、その接続一覧ファイルを破棄して空に戻します。接続を再登録してください。暗号化キーとワークスペース設定は保持し、アクセス権などの入出力エラーでは削除しません。

接続設定でプロバイダー・接続先・認証方式を変更すると、以前の保存済み認証情報は引き継ぎません。OAuthはテナントID・クライアントIDの変更時も再サインインが必要です。「保存済みの認証情報を削除」またはOAuthの「サインアウト」で、この接続の保存済み認証情報を削除できます。サインアウトはこのアプリ内だけに作用し、ブラウザーのMicrosoftセッションは終了しません。接続を削除すると、その接続を選んでいたワークスペースでも再選択が必要です。

OAuthは各APIリクエスト前に保存済みアカウントの有効なトークンを取得し、必要に応じて自動更新します。更新できない場合は再サインインを案内し、実行中にブラウザーを自動で開いたり、APIキーへ切り替えたりしません。CLIでも選択済みのOAuth接続を再利用できます。手動入力のEntra IDアクセストークンは自動更新しません。APIキー・手動トークンの認証では対応する環境変数も使えますが、その値自体は個人設定へ保存しません。

対象ソース、修正候補、必要なルールと周辺コード、検証エラーが、選択したプロバイダーのAPIへ送られます。独立レビューも同じ接続・モデルを使い、修正前・修正後と全対象ルールを別の会話で確認します。大きい入力や出力はページ・記録単位に分けて継続します。

## 2. アプリケーションの起動

### 配布されたアプリを使う

Windowsでは`OneByOne-…-Setup.exe`でインストール後にスタートメニューから、macOSでは配布ZIPを展開して`OneByOne.app`を起動します。MacのアプリはApplicationsへ移動できます。初めて試す場合は、ワークスペースの新規作成ダイアログからデモプロジェクトを作成できます。

左側は上に「LLM接続」、下に「ワークスペース」の一覧があります。接続名を選ぶと独立した接続設定画面、ワークスペース名を選ぶと「対象フォルダ → ルール → 実行設定 → 確認 → 結果確認 → コミット」の6タブが開きます。

### ワークスペースを作成・選択する

「ワークスペース」の「＋」から新規作成します。対象フォルダを先に指定し、名前を付けます。フォルダ選択時にGit管理下であること、初回コミットがあること、リポジトリ全体に未コミット変更がないことを確認し、使用できない場合は対象フォルダ欄に理由を表示します。ステージ済みの変更と未追跡ファイルも確認し、Gitで除外された未追跡ファイルは変更として扱いません。リポジトリ内のサブフォルダも指定できますが、その外側の変更も確認対象です。選択後の変更を検出するため、実行開始時にも同じ条件を再確認します。

IDは固定です。表示名と対象フォルダは後から変更できます。対象フォルダの変更は停止中かつ未保存の変更がないときに行い、以前の実行結果・作業コピーは残し、新しい実行データの保存先を内部で自動的に割り当てます。変更後は「実行設定」で対象ファイルを再抽出し、処理するファイルを選び直します。同じ対象フォルダに対して複数のワークスペースを作れます。

「対象フォルダ」では、フォルダ欄の下にファイル一覧と内容を表示します。左は相対パスと強調したファイル名、右は選択したファイルの行番号付き本文です。パス検索・一覧更新・左右の幅調整と独立したスクロールに対応します。元の対象フォルダを読む機能で、実行するファイルの選択や修正後の結果表示とは独立しています。Gitの管理ファイルと未追跡ファイルを表示し、無視された未追跡ファイル・Git内部ファイル・リンクは除外します。本文はUTF-8 / Shift_JISに対応します。画面の本文表示は先頭20,000行までですが、AI処理の対象行数を制限するものではありません。

ワークスペースは端末内のアプリ用フォルダに保存します。Windowsは`%LOCALAPPDATA%/OneByOne/`、macOSは`~/Library/Application Support/OneByOne/`です。保存済みのワークスペースは起動時に左メニューへ表示され、名前をクリックして切り替えます。

```text
アプリ用フォルダ/OneByOne/
  app-settings.json                         # 選択中のワークスペース
  private/
    master-key.json
    llm-settings/
      <暗号化された接続一覧>.json       # LLM接続の定義
  workspaces/
    <固定ID>/
      setting.json                    # 名前・対象フォルダ・処理設定・LLM接続ID
      rule-versions/
        <版ID>/
          rules.json                 # Markdown文字列の配列（IDはfront matter）
      runs/
        queue.jsonl                   # アプリが管理する実行データ
        ...
  workspace-locks/<固定ID>/
    .edit.lock                        # 同じワークスペースの編集ロック
    rule-locks/                       # 開いているルールの編集ロック
```

対象フォルダにはアプリ設定を作りません。ルールの持ち運びや共有には`rules.json`を使います。受け取った人は自分のワークスペースに読み込み、対象フォルダ・LLM接続・適用ルールを選びます。

「設定を複製」は別のIDで設定をコピーし、キューと実行結果を分離します。同じ登録済みLLM接続を引き継げるので、別のルールや接続を選んで比較できます。同じ端末の別アプリがワークスペースを開いている間は後から開いた側を閲覧専用にし、先行側の切替・終了後に更新して編集権限を取得できます。

以前の形式の設定・ルールは読み込みません。形式の異なるワークスペースは新しく作成し直してください。

`ONEBYONE_CONFIG`とCLIの`--config`でアプリの設定ファイルを変更すると、その親フォルダをワークスペースの保存場所に使います。個人LLM設定の保存先は`ONEBYONE_PRIVATE_DIR`で別途指定できます。配布物に個人設定や認証情報を含めないでください。

### ソースから起動・ビルドする

開発にはGo 1.25以上（ビルド・CIでは1.27.x）、Node.js 22以上、WailsとOS依存環境を用意します。Git・rgは共通コマンドが同梱用資材を自動取得します。リポジトリ直下の共通コマンドでテスト・ビルド・配布物作成を行います。

```sh
npm --prefix frontend ci
npm test
npm run build
npm run package
```

`npm test`はフロントエンドの型検査、スクリプト・Goのテスト、Go vetをまとめて実行します。`npm run build`はGUIとCLIを`build/bin/`へ出力し、Git・rgとライセンスを同梱します。`npm run package`はビルド後に配布フォルダとZIPを作成し、WindowsではSetupも生成します。Go・Node.js・Wails・NSISなどのビルド用ツールは事前に導入してください。OS・CPU指定、同梱資材、出力先などは[ビルド・配布手順](docs/build.md)を参照してください。

WindowsのCLI名は`onebyone-cli.exe`です。Go・Node.jsは開発用で、ビルド済みアプリの利用者には不要です。画面だけを確認する場合は次のコマンドを使えます。ブラウザ版はプレビュー用データを表示し、ファイル操作やAI実行を行いません。

```sh
npm --prefix frontend run dev
```

## 3. 操作

### デモで試す

1. 「ワークスペース」の「＋」を押し、対象フォルダのラベル右にある「デモプロジェクトを作成する」を選びます。
2. 「デモ保存先のディレクトリを選択」で保存先を指定します。その下の新しい`onebyone-demo-<ID>/`に28ファイルを作成し、Gitの初期化と初回コミットを済ませて対象フォルダに設定します。既存のファイルは上書きしません。
3. ワークスペースを作成すると、`src/**/*.js`全体を対象にする3件と、さらに本文条件で絞る10件のルールが自動で入ります。
4. 「実行設定」を開くと`src/`内の23ファイルを自動抽出します。登録済みのLLM接続を選び、処理しないファイルのチェックを外します。「確認」で選択済みファイルと候補ルールを見て「実行」を押します。進捗と停止操作、実行後の差分は「結果確認」にまとまっています。

架空の配送・請求管理アプリが、SDK「Parcel Kit」から後継の「Parcel Client」へ切り替える題材です。入れ子のフォルダへ実践的な変更ケースを配置しています。トランザクションの解放、購読の所有権、ページ単位の非同期処理、flushと完了通知の順序、再試行時の冪等性、全件検証後の予約など、名前の置換だけでは済まない例を含みます。変更不要4ファイル、外部契約の確認が必要な4ファイルもあり、`done`・`skipped`・`needs_human`を比較できます。状態は実際のAI判断と検証結果から決まります。

大きな複合例として`src/workflows/dispatch-cycle.js`も含みます。配送計画から在庫予約、決済、帳票公開までを一つのファイルで扱い、全13件のルールに実際の修正箇所があります。デモも通常の処理と同じく、計画・編集・レビューを分割保存しながら完了まで継続します。

API名は `TransactionManager`、`RecordDirectory` など用途を表す通常の名前です。ルールはAPIの契約と判断基準を中心に記述し、変更前後のコードは別用途の短い例にしています。対象ファイルの全文や完成コードは含めず、実ファイルの前後関係に合わせて適用する構成です。

部分採用を試す場合は`src/shared/host-transaction.js`を選びます。ローカルの下書き保存は関数内でトランザクションを完結できるため修正でき、外部ホストへ渡す編集処理は終了責任が不明なため保留するケースです。同じファイル・同じルール内で「修正済み」と「要確認」が混在し、保留箇所で使う旧importを残す判断も必要です。今回のデータは新しく作成するデモに含まれ、作成済みフォルダは自動更新しません。

デモ作成とルールの自動導入はオフラインです。処理実行には通常のLLM接続と利用料金が必要です。標準チェックは編集範囲・候補の整合性と独立レビューで、JavaScriptの構文・動作テストは含みません。Node.jsやパッケージの追加インストールなしで操作できます。題材と各ファイルの説明は[デモプロジェクトのREADME](internal/demopreset/project/README.md)にあります。

### GUIから実行する

1. 左メニューの「LLM接続」の「＋」で名前付き接続を登録します。プロバイダー・モデル・接続先・認証情報を設定し、必要に応じて「接続をテスト」を利用します。
2. 「ワークスペース」の「＋」から対象フォルダを選んで新規作成します。作成済みの場合は、左メニューのワークスペース名をクリックします。
3. 「対象フォルダ」で対象パスを確認します。「変更」から別のGit管理フォルダへ切り替えられます。Git管理下でない、初回コミットがない、未コミット変更がある場合は、その場でフォルダ欄にエラーを表示し、変更を保存しません。
4. 「ルール」で「…」からJSON・CSVを読み込むか、ルールを追加します。ID・名称・説明・対象ファイル・内容の条件を編集します。本文は「Preview」でMarkdown表示し、「</>」で原文の編集に切り替えます。プレビューには未保存の編集も反映されます。一覧と詳細のアイコンは条件の指定状態を示し、パスのみはフォルダ（黄）、内容のみはファイル（青）、両方空欄は共通（緑）、両方指定は箱（赤）です。アイコンにカーソルを合わせると種別名を表示します。未保存のルールには黄色の編集アイコンが付きます。画面移動時にまとめて保存し、必須項目の空欄・不正なパターンなどのエラーは一覧と詳細へ表示します。下書きはエラーがあっても保持します。
5. 「実行設定」で登録済みのLLM接続と適用ルールを選びます。適用ルールは初期状態ですべて選択され、変更した場合は「対象を更新」で再抽出します。選択しないルールは修正・独立レビューに渡しません。この画面を開くと対象ファイルを自動抽出し、本文に一致した候補ルールを表示します。初回は全件が選択済みです。処理しないファイルのチェックを外し、この画面で対象を確定します。まず少数のファイルで試してから対象を広げられます。
6. 「確認」には選択済みファイルと候補ルールだけを表示します。対象を変える場合は「実行設定」へ戻り、内容がよければ「実行」を押します。確認画面では再抽出や選択変更を行わないため、確定後に対象が増えることはありません。
7. 実行すると「結果確認」へ移動します。現在の状態・進捗を上部で確認し、ファイルをクリックすると差分や適用ルールを表示します。検証結果・履歴などの補足情報は必要なときに開きます。

新規ワークスペースのLLM接続は未選択です。接続を編集すると、その接続を選んだワークスペースでは次回実行から更新した設定を使います。LLM接続の定義は独立して管理できます。ワークスペースで使う接続の選択変更には、そのワークスペースの編集権限が必要です。実行中のワークスペース・接続の切替は行えません。「接続をテスト」と実際の処理にはAPI料金が発生する場合があります。

ルールの自動保存は複数の下書きを一括検証し、すべて成功した場合に1つの新しいローカル版として採用します。読み込み元のJSON・CSVと以前のルール定義は保持します。同じキューで「実行設定」へ戻ると再抽出し、以前の選択と処理履歴を引き継ぎます。ルール・対象・抽出条件を変更した後は、この画面で再抽出して対象を確認します。対象やルールの未設定・エラー、再抽出前の古い一覧がある間は「確認」へ進めません。LLM接続の未設定も実行前に解消します。

同じローカル設定を別のアプリが編集している場合は閲覧専用で表示します。開いた後にルールが更新されていた場合も保存を拒否するため、最新の内容を開き直して確認します。

実行設定・確認は、左にファイル一覧、中央に次回処理するファイルの内容、候補ルールをクリックすると右にルール詳細を表示します。実行用の作業コピーがある場合は、その現在の内容を表示します。状態は一覧の各行と本文ヘッダーの右端、候補ルールは本文ヘッダーのファイル名のすぐ右です。実行設定の左一覧ではルールIDを表示しません。実行設定ではファイル名の左のチェックボックスで対象を選び、確認では確定した選択を読み取り専用で表示します。未選択や接続・設定エラーなどで次へ進めない場合は、ボタンやタブにカーソルを合わせると理由が表示されます。

ターン数・試行回数・検証回数・処理時間・出力トークン数・対象ファイル容量・費用の上限設定は、GUI・CLI・APIから廃止しました。過去に保存した上限値も読込時に破棄し、再保存しません。処理は完了、人の判断が必要な保留、ユーザー停止、回復できないエラーまで継続します。料金単価は推定料金の集計にだけ使います。

チェックの選択は画面移動時に保存します。外したファイルは履歴を残したまま処理対象から除外し、選択済みの`pending`・`failed`を実行し、チェックした`needs_human`（要確認）も履歴・計画を保持して再試行に追加します。要確認だけの選択でも「次へ」に進めます。完了・変更不要は再試行操作で戻した場合だけ実行します。選択件数と今回実行できる件数は区別して表示します。対象フォルダを変更した場合は実行データを分離し、再抽出した一覧を実行設定で確認します。別の対象フォルダやワークスペースへ選択を引き継ぎません。内部キューは1行1ファイルのJSONLです。

```jsonl
{"file":"src/A.ext","rules":["R019"],"status":"pending","attempts":0}
{"file":"src/B.ext","rules":["R019","R020"],"status":"pending","attempts":0,"excluded":true}
```

`file`は相対パス、`rules`は機械的な候補、`excluded: true`は利用者がチェックを外した状態です。省略時は選択済みです。`rulesApplied`は採用した修正計画から導出し、候補とは別に記録します。GUI・CLIともキューはワークスペース単位で自動管理します。処理対象の変更は画面のチェックボックス、またはCLIの`selection`で行います。

### 1ファイルの内部処理

```text
対象ソース＋候補ルール＋共通プロンプト
  → 独立した会話を開始
  → read_rulesで必要な個別ルール本文をまとめて取得・必要時に周辺コードを取得
  → update_stateで箇所別計画を少しずつ登録
  → stage_editsで編集を追加・修正して保存
  → validate_staged_candidateで保存済み全編集を組み立てて検証
  → メモリ上で元ファイルのハッシュ・編集範囲・変更案の整合性を確認する
  → 不合格なら同じ会話で修正を続ける
  → 修正担当が合格済みcandidateIdで最終回答
  → 別コンテキストのLLMが修正前・修正後・全必須ルールを独立レビュー
  → 要修正なら同じ編集会話へ戻す。判断保留なら要確認で停止
  → 機械検証・独立レビューの両方に合格した候補だけを1ファイル1コミット
  → JSONLと試行履歴を保存
```

AIに任意ファイルを書き込むツールやシェル実行ツールを渡しません。編集パスはアプリが固定します。参照する周辺コードも対象フォルダ内の範囲指定に制限し、シンボリックリンクや設定・認証関連ファイルを除外します。

ファイルごとの修正・検証・独立レビューは並列で実行します。既定は2ファイル、実行設定で1〜10に変更でき、1なら逐次処理です。同じ実行では全ファイルが実行開始時のGitコミットを参照し、途中の採用で入力が変わることはありません。Gitへの反映・コミット・台帳更新は1件ずつ処理します。

AIは`update_state`で計画を、`stage_edits`で編集を少量ずつ追加・更新します。同じIDを再提出すればその項目だけを差し替え、他の保存済み作業は残ります。最後に`validate_staged_candidate`で全編集を検証するため、毎回の全件再提出は不要です。原文・候補・ルール・保存状態は読込ツールでページ取得できます。詳細は[AIハーネス](docs/ai-harness.md)を参照してください。

検証コマンドは実行しません。機械検証は編集範囲と変更案の整合性を確認し、ルールを満たすかは別コンテキストのLLMが確認します。複数ファイルの変更を同時に必要とするケースは人の確認へ回します。

独立レビューは、修正担当の会話・計画・説明や以前のレビュー指摘を受け取らず、元ファイルのパス・内容で確定したルールをすべて確認します。共通ルールも該当箇所がなければ、理由付きの「対象外」を許可します。指摘にはルールID、該当箇所、理由、修正方針を記録します。要修正の候補は採用せず、修正後に機械検証と新しい会話でのレビューを受け直します。変更不要と判断したファイルも変更前と同じ本文を独立レビューへ渡します。レビュー指摘を受けた後に`skipped`へ切り替えて指摘を回避することはできません。

会話が長くなったら保存状態を引き継ぐ新しい会話へ切り替え、出力途中切れでは不完全な応答を捨てて小さな単位で再生成します。保存済みの計画・編集・レビュー指摘は残ります。独立レビューの分割モードでも、原文・候補・全ルールの読込と評価を完了しなければ合格できません。

通信断、HTTP 408・429・5xxなどは待機して再送し、待機中も停止できます。`Retry-After`があれば指定された時間を使います。認証失敗など回復できないエラーは停止理由を残します。使用量が取得できなかった要求は`usage.uncertain: true`を保存し、一部未計上として表示します。再送分を含む実際の請求額まで保証するものではありません。

停止後は同じ対象を再試行に戻し、保存した計画・編集・候補から再開できます。元データが同じなら、独立レビュー待ちの候補はレビューから復帰します。過去の使用ターン・トークン・推定料金は履歴として保持します。

### CLIから実行する

GUIを開かずに、ワークスペース作成、LLM接続、ルール取り込み、実行、結果確認、新規ブランチへの結果反映まで操作できます。GUIと同じ処理とローカル保存先を使います。以下は開発ビルドのmacOSの例です。Windows PowerShellでは実行ファイルを`./build/bin/onebyone-cli.exe`に読み替えます。

```sh
./build/bin/onebyone doctor
./build/bin/onebyone workspace create --name "API更新" --root ./project
./build/bin/onebyone rules import --input ./rules.json --mode replace
./build/bin/onebyone llm save --input ./connection.json
./build/bin/onebyone llm list --json
./build/bin/onebyone llm select --id <接続ID>
./build/bin/onebyone scan
./build/bin/onebyone selection --all
./build/bin/onebyone run --limit 20 --concurrency 2
./build/bin/onebyone runs list --json
./build/bin/onebyone report --output ./result.json
```

Azure OAuthは`llm login --id <接続ID>`でブラウザーからサインインできます。APIキーは接続JSONまたは環境変数で渡し、JSONを標準入力から読む場合は`llm save --input -`を使います。接続の選択後は`llm test --id <接続ID>`で確認できます。このテストは実際にモデルを呼びます。

`demo --directory ./demo-projects`でGitの初回コミット・ルール・対象一覧を持つデモを作成できます。LLM接続は別途設定します。既存のワークスペースは`--workspace <ID>`で指定し、省略時は選択中のものを使います。キュー・実行結果の保存先は自動管理します。

`run`または`run --limit 0`は選択済みの未修正・失敗ファイルを件数制限なく処理します。Ctrl+Cは停止と保存を待ちます。`--json`は標準出力をJSONにし、進捗・エラーは標準エラーへ出します。終了コードは正常`0`、操作エラー`1`、今回の実行対象に失敗・要確認が残る場合`2`、割り込み`130`です。

`run --concurrency 1〜10`で並列数を指定するとワークスペースへ保存します。省略時は保存済み設定、未設定なら2です。GUIとCLIは同じ設定を使います。

`publish preview --json`で反映対象と本文を確認し、`publish create --input ./publication.json`で新規ブランチへ1コミットで反映できます。入力には確認した`workspaceId`・`revision`と、新規ブランチ名`branch`・必須タイトル`title`を指定します。`message`を省略するとプレビューのサマリーを本文に使います。

[CLIの使い方](docs/cli.md)に、接続JSON、ルール編集、設定の部分更新、ファイル選択、実行ごとの詳細・レポート、再試行・変更破棄、結果反映、保存先の分離をまとめています。

## 4. 結果確認

「結果確認」は現在の状態と進捗、ファイル一覧、選択したファイルの詳細をまとめた画面です。上部で処理中・待機中・要確認などの件数を確認し、状態やファイル名・ルールで一覧を絞り込めます。停止操作もここで行います。

一覧ではファイル、状態、適用ルールをコンパクトに表示します。ファイルをクリックすると修正差分を開き、適用ルールをクリックするとその内容を確認できます。検証結果・過去の試行・使用量などの補足情報は、見たい項目を選んで表示します。「検証」と「履歴」の独立レビューを開くと、判定・指摘箇所・ルールごとの評価を確認できます。処理前の候補ルールと、採用した計画の適用ルールは区別します。除外したファイルの履歴も保持します。「結果を出力」では保存ダイアログでファイル名と出力先を指定し、結果JSONを保存します。キャンセルした場合は出力しません。

一覧と詳細の境界をドラッグして幅を調整できます。初期表示は一覧を内容に合わせた幅にし、詳細を広く取ります。選択したファイル名の横に適用済みのルールID、その直下にLLMの説明を表示します。説明はタブを切り替えても確認でき、過去の試行を選ぶとその試行の説明に切り替わります。

「変更内容」では、差分の各修正箇所にルールIDとルールの説明を並べ、その下に修正担当LLMが記録した具体的な修正内容と状態を表示します。採用時の定型文や判断の詳細はコード上には表示しません。「修正済み」は検証・独立レビューを通過して実際にコミットした項目だけです。ファイルが要確認で終了した場合、保留箇所は「要確認」、その他の対応案は「未反映」と表示し、部分的な修正はコミットしません。

出力JSONの各試行の`changes`にも、同じ対応状況とルール名・リスク・保留理由を保存します。過去の試行は当時の記録を表示し、古いデータに記録のない項目は「未記録」と表示します。

| 状態 | 意味 |
|---|---|
| `pending` | 未処理、または手動で再実行を指定 |
| `running` | そのファイルの試行を実行中 |
| `done` | 機械検証と独立レビューに合格し、専用ブランチにコミット済み |
| `skipped` | 独立レビューでも追加の修正が不要と確認した |
| `failed` | 失敗し、再試行の対象 |
| `needs_human` | 人の判断が必要な保留、未対応の入力、整合性の問題など |

`done`は実施した機械検査と独立レビューの合格を示します。LLMのレビューにも見落としはあるため、対象プロジェクトの動作テストを併用してください。ビルド・テストはアプリ内で自動実行しません。変更不要の申告も独立レビューで確認します。

キューと実行結果は端末内の`workspaces/<ID>/runs/`でアプリが自動管理し、画面には保存先の設定を表示しません。既存ワークスペースに記録済みの保存先は引き継ぎ、履歴を保持します。結果レポートの書き出しは、これまでどおりダイアログで出力先ファイルを指定できます。

```text
runs/
  queue.jsonl                 # 対象・選択/除外・状態・試行履歴・使用量
  queue.jsonl.session.json    # ルールハッシュ・元コミット・作業コピー情報
  queue.jsonl.publications.json # 反映先ブランチ・コミットと反映履歴
  queue.jsonl.artifacts/      # 各試行の変更前・変更後・差分・修復状態・独立レビュー
  queue.jsonl.worktree/       # 採用済み修正を持つ専用Git作業コピー
  reports/                    # CLIの report コマンドによる結果JSON
```

細かい作業履歴は結果画面の作業コピーと`onebyone/...`ブランチに保持します。SourceTreeなどでまとめてレビューする場合は、次の「コミット」で新規ブランチを作成します。元のブランチへのマージやチェリーピックは、利用者が確認後に行います。アプリは自動でマージ・プッシュしません。

要確認の箇所が特定できる場合は、ルールID・理由と対象行を記録します。結果詳細の「要確認」から該当行へ移動でき、コード内にも理由が表示されます。修正されなかった行も確認できます。以前の行情報がない記録は「位置未特定」として表示します。

要確認の理由をもとにルールを改善した場合は「実行設定」へ戻って候補を更新し、必要なファイルを再試行に追加します。CLIの`retry --rule R019`は、`rulesApplied`にR019が記録されているファイルを選びます。再試行は対象を`pending`に戻し、履歴と通算の利用量・料金を保持します。元データとルールが同じなら計画・保存済み編集・候補も復元します。ルールごとの候補件数・適用件数も確認できます。

変更内容に併記する対応状況は、具体的な対応内容が記録された項目だけを表示します。新しい候補では修正箇所とルールを対応付け、変更前・変更後の行番号を保存します。差分の該当行の上にあるルールIDへカーソルを合わせると名称、クリックすると右側にルール詳細を表示します。行の対応が記録されていない過去の結果には、推測でアイコンを付けません。

結果詳細の「変更破棄」は、確認後にそのファイルの採用済み変更を取り消し、作業コピーの処理開始前の内容へ戻します。元の対象フォルダや別ファイルは変更せず、取り消しのコミットと履歴を残します。ファイルは「再試行」になり、次の実行では新しい計画を作ります。以前の試行・差分・通算料金は保持します。変更済みファイルを再実行して「変更不要」になった場合も破棄できます。採用済み変更がないファイル、実行中、閲覧専用の場合は無効です。

再抽出や再起動でも既存ファイルの選択・除外と履歴を保持します。新しい抽出範囲から外れた未完了ファイルは、`needs_human`にして自動処理から除外します。CLIもワークスペースが管理するキューと、選択済みの個人LLM接続を使います。

## 5. コミット

「コミット」で、採用済みの最終結果を新規ブランチへ1コミットでまとめます。ブランチ名は候補から編集でき、コミットタイトルは必須入力です。本文は対象・修正済み・修正不要のファイル数と、ファイルごとの変更概要と、各ルールのID・Title（名称）をH4見出しにし、その下に「修正の内容」（修正担当LLMが記録した採用済みの修正）と「修正後レビュー結果」を省略せず初期表示し、編集できます。各ファイルのH2見出しの直前に区切り線を置きます。ファイルパスはリポジトリ相対のMarkdownリンクにします。Gitのコミット本文はプレーンテキストのため、リンクとして操作できるかは表示するクライアントに依存します。 アプリでは本文の「</> / Preview」を切り替え、原文側で編集できます。Preview内のファイルリンクを選ぶと、右から差分パネルが開きます。左端のグリップで幅を変更でき、閉じるボタンまたはEscapeキーで戻れます。

対象は処理開始時から現在までの累積差分です。再試行による修正はまとめ、変更破棄で元に戻した箇所・未採用の候補・差分がないファイルは含めません。現在の実行選択や履歴の表示対象とは独立して、ワークスペースの最終結果を使います。ファイルを選ぶと反映前に差分を確認できます。

反映ボタンは、処理開始時のコミットを親にした新規コミットとブランチを作成します。既存ブランチは上書きせず、元フォルダのファイル・チェックアウト中のブランチ・内部の作業履歴を保持します。アプリは反映先をチェックアウトしないため、元フォルダをSourceTreeなどで開いて、反映先ブランチへ切り替えてレビュー・マージできます。プッシュは行いません。プレビュー後に修正結果が変わった場合は再確認を求めます。

反映履歴はワークスペースに保持します。反映後の再試行・変更破棄は過去の反映先ブランチを変更しません。最新の結果を出し直すときは、新たなブランチ名を指定します。

動作検証は、rgの実ファイル照合、ローカルのモックAPI、使い捨てGitリポジトリを使用したテストで行います。実際のLLM接続には利用者の接続情報が必要です。Windows実機での起動・WebView2・署名済み配布の確認は、Windows CIと実機確認で別途実施してください。配布用証明書によるコード署名とmacOS公証は、この初版では未設定です。

```sh
npm test
npm test -- --race
```
